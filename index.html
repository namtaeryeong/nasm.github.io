비정형 텍스트 자동 정제 (Pydantic 검증기)

BACKEND_SERVER.py · ProductCollectRequest

구현 목적

크롤러가 넘겨주는 원재료·영양정보는 상품마다 괄호, 슬래시, 제조사 코드, 알레르기 문구가 뒤섞인 문자열입니다. 판정 로직이 이걸 그대로 받으면 매번 예외가 생기기 때문에, 요청이 서버에 들어오는 순간 표준 형식으로 바꾸도록 설계했습니다.

처리 과정

  1. 용량: 숫자 외 문자를 지워 float로 변환
  2. 원재료: NFKC 정규화 → 알레르기·제조시설 괄호 제거 → -지엘 같은 제조사 코드만 lookahead로 삭제 (L-글루탐산은 보존) → 아몬드/미국산을 아몬드(미국산)으로 통합 → 중첩 괄호 계층 분리 → 중복 제거 · 정렬
  3. 영양정보: 총 내용량 Ng … Mg당 Kkcal 패턴을 찾아 (N/M)×K로 총 열량 환산, 나머지 9개 항목은 키워드별 수치 추출 후 JSON 문자열로 저장

사용 기술

Pydantic v2 field_validatorreunicodedatajson

@field_validator('current_ingredients', mode='before')
@classmethod
def clean_ingredients(cls, v):
    if isinstance(v, str):
        v = unicodedata.normalize('NFKC', v).upper()
        v = re.sub(r'\(.*?(함유|제조|시설).*?\)', '', v)
        v = re.sub(r'-(지엘|믹스|MIX|씨제이|대상의|기타)(?=[,/\s:\]\)]|$)', '', v)
        v = re.sub(r'([가-힣\w]+)/([가-힣\w]+)', r'\1(\2)', v)
        v = re.sub(r'([가-힣\w]+)\(([^()]+)\(([^()]+)\)\)', r'\1, \2(\3)', v)
        v = v.replace('[', ',').replace(']', ',').replace('{', ',').replace('}', ',')
        items = [i.strip() for i in v.split(',') if i.strip()]
        return ", ".join(sorted(list(set(items))))
    return v

@field_validator('current_nutrition', mode='before')

API 서버 · 크롤러 중계 · 분석 오케스트레이션

BACKEND_SERVER.py

구현 목적

프론트엔드는 백엔드 API 3개만 알면 되도록 하고, 실제 수집은 다른 네트워크에 있는 크롤러 서버에 위임했습니다. 백엔드가 수집 · 정제 · DB 대조 · AI 추천을 한 요청 안에서 조율합니다.

처리 과정 · 상품 상세 분석

  1. GET /product-detail/{kurly_id} 수신
  2. ngrok 주소의 크롤러 /api/detail 호출 (timeout 90s, 브라우저 경고 우회 헤더)
  3. 원본 JSON을 ProductCollectRequest(**live_data)로 검증·정제
  4. perform_analysis()에서 DB 조회 → 최초면 INSERT, 기존이면 변동 비교
  5. Gemini 대체 식품 3종을 붙여 응답, ?update=true면 기준 데이터 UPDATE

카메라 촬영 성분표 OCR 파이프라인

vision_engine.py · vision_parser.py · /api/v1/ocr-scan

구현 목적

오프라인 매장에서도 성분표를 찍으면 검색 결과와 같은 분석을 받을 수 있도록 했습니다. OCR 모델을 직접 학습하는 대신 Gemini Vision에 추출 규칙을 지시하고, 결과는 정규식으로 다시 검증하는 구조를 택했습니다.

처리 과정

  1. 업로드 이미지를 uuid 파일명으로 임시 저장 (처리 후 finally에서 삭제)
  2. Gemini Vision에 temperature=0.0, “요약·정리 금지, 괄호·%·슬래시 그대로” 프롬프트로 1차 추출
  3. parse_ocr_text()가 번호 형식 라인을 읽어 상품명·용량·원재료·영양정보를 딕셔너리화. 열량 문장에 총량이 없으면 앞서 읽은 용량을 사용
  4. 공백을 무시한 상품명으로 DB 기준 데이터 매칭 → 변동 비교 → 대체 식품 추천

구현 목적

구현 목적

정제된 데이터를 어떻게 활용할 수 있는지 보여주는 응용 기능입니다. DB에 저장된 과거 기준과 현재 데이터를 비교해 용량 감소(슈링크플레이션), 원재료 삭제·추가·함량·원산지 변경(스킴플레이션), 영양 수치 변동을 구조화된 리포트로 만듭니다.

처리 과정

  1. extract_ingredient_meta()로 "아몬드(미국산) 76.492%"를 이름·원산지·함량 객체로 분해
  2. 이름을 키로 한 맵끼리 비교해 삭제·추가 성분 추출, 같은 이름이면 함량 감소·원산지 변경 확인
  3. 영양성분 9개 항목은 차이가 0.1을 넘을 때만 변동으로 기록

이 결과를 바탕으로 한 AI 경고 문구(get_ai_comprehensive_insight)는 서버에서 생성되지만 시연 화면에는 노출하지 않았습니다.

        if past['percent'] > 0 and curr['percent'] > 0:

문제

크롤링 데이터와 OCR 데이터가 서로 다른 모양으로 들어와, 판정 로직에서 경로마다 예외 처리가 필요했습니다.

해결

정제를 “입구”로 옮겼습니다. 크롤링 경로는 Pydantic 검증기, OCR 경로는 parse_ocr_text()에 같은 정규식 규칙을 적용해 두 경로가 동일한 스키마로 수렴하도록 만들었습니다.

문제

제조사 코드 -지엘을 지우려고 하이픈 뒤를 지우면 L-글루탐산 같은 실제 성분명까지 깨졌습니다.

해결

삭제 대상을 코드 목록으로 한정하고, 뒤에 구분자가 오는 경우만 매칭하는 lookahead (?=[,/\s:\]\)]|$)를 써서 성분명은 보존했습니다.

문제

Gemini가 성분표를 “보기 좋게” 요약하거나, 대체 식품 응답에 마크다운을 붙여 파싱이 실패하는 경우가 있었습니다.

해결

OCR은 temperature=0.0과 원문 보존 지시로 자의적 해석을 줄였고, 추천은 JSON 배열만 허용 + 코드 펜스 제거 + 실패 시 기본값 반환으로 서비스가 멈추지 않게 했습니다.

문제

OCR로 읽은 상품명은 띄어쓰기가 DB와 달라 같은 상품인데도 매칭에 실패했습니다.

해결

SQL에서 REPLACE(product_name, ' ', '')로 공백을 제거한 값끼리 완전 일치 비교하도록 바꿨습니다. 부분 일치(LIKE)보다 오매칭 위험이 낮습니다.

API 엔드포인트

프론트용 3개(검색·상세·OCR)와 관리자·부가용 2개로 역할을 나눈 REST API.

개발 과정에서 겪은 어려움

  • 초기에 주제를 넓게 잡아 개발 도중 판정·탐지 로직을 여러 번 바꿨습니다. 기능의 중심(영양 판정)과 부가 기능(변동 탐지, 리뷰 분석)을 늦게 구분한 것이 원인이었습니다.
  • 정규식 정제는 표준 형식에서는 안정적이었지만, 기준량이 뒤집힌 표기나 구분자가 없는 텍스트에서 실패했습니다. 평가로 실패 유형을 4가지로 분류해 다음 개선 대상을 명확히 했습니다.
  • 크롤러가 다른 네트워크에 있어 ngrok 주소와 응답 시간에 의존했고, 크롤러 응답 실패를 error JSON으로 돌려주는 처리를 추가했습니다.

얻은 역량

  • 외부 서버·AI API가 섞인 요청을 하나의 API로 조율하는 서버 설계
  • 신뢰할 수 없는 입력을 진입 시점에서 검증·정규화하는 습관 (Pydantic, 정규식)
  • 생성형 AI 결과를 규칙 기반 로직으로 재검증하는 이중 처리 구조
  • 기능을 “돌아간다”가 아니라 정확도 수치로 검증하는 평가 방식
  • 프론트·크롤러 담당과 데이터 키·응답 형식을 맞추는 협업
